## 2. Speckit Features That May Follow, In Order (Ruling 112)

Each feature is gated on task 1.2 and is created from the assembly root `opensoft/openPractice` on its base branch, in the order below. A feature's gate lists what must have merged before it starts. Every feature is accepted against synthetic data only (TH-16). A real practice's money first moves through openPractice at beta acceptance, which FD-8 sets as one live remittance posted end to end and one live merchant settlement reconciled to a bank line. That needs features 5 and 6, and the foundation's deposit explanation (BAB-14). Separately, as a PROPOSED gate (design call CR-67): no real practice's money passes through openPractice in features 1 to 3, because refunds, credit-balance cases and chargebacks arrive in feature 4. Owner question 14 in `design.md` asks whether refund recording should move into feature 2.

The foundation change's four features slot in as `design.md` Decision 1 sets out: its Feature 1 (patient registry) comes before feature 1 below; its Feature 2 (EHR patient link) may run alongside features 1 and 2; its Feature 3 (accounting contract and ERPNext adapter) follows feature 1 and, for go-live, PA-1; and its Feature 4 (clinical-fact consumption) is folded into features 2 and 3 below, as its task 2.4 allows (PA-3).

Where a feature needs a capability that another change's feature owns and that feature has not yet landed, the gate below names it, and the feature is built and accepted against a stand-in for it; the part that needs it goes live only when the owning feature lands (design call CR-89, PROPOSED).
